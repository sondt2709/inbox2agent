# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`i2a` (inbox2agent) is a Go CLI. It polls chat and work tools for new messages and sends them in batches to an AI agent. The agent sends its results back as cards with `i2a card add`; the user reads them in the Feed tab of `i2a`, sends replies from there (`r`) and asks the agent for more about a card (`t`). The agent can send a reply with `i2a reply`. The agent saves the file of a WhatsApp message with `i2a download`. Accounts: Mattermost and WhatsApp now; GitHub and Linear later.

The model has five items, each with one job. An **account** is one login; it only connects. A **conversation** is one DM, group or channel of an account; it is in one space or more, and each link (an entry in `[[spaces.conversations]]`) has its own read level (`all`, `mentions` = messages for the user, or each message of a direct conversation, `off`). A **space** is a group of conversations that the user names; it is the only item that names an agent and a schedule. An **agent** is how to send a batch (the old profile). A **schedule** is when a space sends. The built-in space **Unsorted** (`config.UnsortedID`) holds each conversation that no space lists; its agent can be empty (hold). Accounts, agents, schedules and spaces have a stable `id` and a `name` that the user can change; a conversation has the platform `name` and an optional `label`. Use these words in code, docs and errors; do not say source or profile for them (`internal/source` is the platform adapter that reads one account). Drivers: `orca` (the Orca CLI) and `dry-run`. One static binary (`CGO_ENABLED=0`), macOS first.

## Architecture

Data flow: `source.Source.Collect` (read level of each conversation: `config.Level`, `Env.Levels`, `Env.Default`; `Message.ReplyTo` for a quote or a thread reply) → `store.SavePoll` (messages and cursor in one transaction) → `daemon.Run` (one next send time for each space: `config.Schedule.Next`) → `daemon.Engine.Dispatch(spaces)` → `config.Links` (conversation → each space that lists it, computed at send time, so a moved conversation takes its waiting messages; `config.Wants` filters each link with `Message.ForMe`) → `render.Render` (sanitize, digest file, prompts, card section) → `agent.Driver.Deliver` (session of the space) → `store.FinishDispatch` (`messages.space`, `dispatches.space` and `agent`).

Return path: the agent runs `i2a card add` (JSON on stdin) → `card.Parse` and `card.Prepare` (validate, sanitize, cut) → `card.Handle` (`ORCA_TERMINAL_HANDLE`) and `card.AgentSession` (`CLAUDE_CODE_SESSION_ID`) → `store.SaveCards` (one transaction, upsert by key) → `card.Plan` → notifications. The Feed tab reads the cards every 2 seconds. `i2a card add` writes the store directly; it does not talk to the daemon.

Reply path: the Feed form (`r`, `ctrl+s`) or `i2a reply` → `reply.Send` (text check, duplicate rule) → `store.StartReply` (`sending`) → `daemon.BuildReplier` → `source.Replier` (`mattermost.Source.Reply`: `GET /posts/{id}`, then `POST /posts?set_online=false`; WhatsApp: `POST /v1/reply {reply_id}` to the daemon, which sends with `whatsapp.Source.Reply` on its connection, else a connection of this process when no daemon answers) → `store.FinishReply` (`sent` or `failed`) → the card becomes `done`. A Mattermost reply does not use the daemon.

Download path: `i2a download --message <id>` → `daemon.Download` (`POST /v1/download {message_id}`: the daemon writes `<data>/tmp/download-*`, never the bytes in the API; else a connection of this process) → `download.Name` (base name only) → `download.Move` (`os.Link`, never overwrite, `name (1).ext`) → `download.Quarantine` (`com.apple.quarantine`) → print the path. i2a never downloads without this command and never records or deletes the file.

Ask path: the Feed form (`t`, `ctrl+s`) or `i2a ask` → `ask.Send` (text check, `ask.Resolve`: space of the newest ref message, else `config.Route` of it; the agent of the space; no agent or dry-run refused with `ask.NoAgentError`) → `store.StartAsk` (`queued`) → `agent.Lock` (`<data>/space-<id>.lock`) → `render.Ask` → `agent.Driver.Ask` (the terminal of the card while it runs the Claude session of the card, else `Deliver`) → `store.FinishAsk` (`sent`, `failed`, or still `queued` when the agent is busy for `ask.Wait`). `Engine.Dispatch` sends queued asks with `ask.Retry` before the batches, and `daemon.Run` tries them at least each minute (`askEvery`). The agent answers with `i2a card add` and the key of the card.

- `internal/inbox`: shared types (`Message`, `Cursor`, `Card`, states). It prevents import cycles between the source, store, render and agent packages.
- `internal/config`: version 2 of `config.toml` (`[[accounts]]`, `[[agents]]`, `[[schedules]]`, `[unsorted]`, `[[spaces]]`, `[settings]`). `Load` converts a version 1 file (`migrate_v1.go`), keeps `config.toml.v1.bak` and returns `Config.Migration`; the CLI prints it to stderr, the daemon logs it. `Links`, `Routes`, `Route` (the first space, for the screens), `Level` and `Levels` (the widest level of the links, which the source reads), `SetConversation` (move to one space), `AddLink`, `SetLevel`, `SetSpaces` (all links of a conversation in one step; the dashboard uses it), `SetLabel`, `SpacesUsing` and `Replace` are the only ways to read or change routes. `config.Update` (lock, read the file, change, validate, write) is the only way to change the file; `Save` also holds the lock. The file is the interface for agents: there is no item command (`i2a conversation` only prints how to edit the file). `save` writes `#:schema ./config.schema.json` as line 1 and `config.schema.json` next to the file. `Schema()` (`schema.go`) builds the JSON Schema from the struct tags (`toml`, `comment` or `doc`, `enum`, `pattern`, `min`, `max`, `schema:"required,id"`); a new field needs a `doc` tag, and `docs/config.schema.json` must be written again with `go test ./internal/config -run TestSchemaCopyIsCurrent -update`. `i2a config check` uses `Parse` and `render.CheckAgents`. `Schedule.Next` gives aligned send times (the start of the hours plus a multiple of `every`); the daemon, `i2a status` and the TUI use it.
- `internal/source`: the `Source` interface and `Build`. A source reads one account and returns messages and the next cursor. It never writes to the store.
- `internal/source/whatsapp`: a linked device of a personal account, made with whatsmeow. The process that collects (the daemon or `i2a run --once`) holds the connection and locks `<data>/whatsapp-<id>.lock`. The whatsmeow event handler writes each message to `wa_messages` in `<data>/whatsapp-<id>.db` (the same file holds the device keys, mode 0600); `Collect` reads the rows after the cursor `{"rowid": n}`. Pairing runs in the TUI or in `i2a account add whatsapp`, never in the daemon. `ReadDevice` reads the phone number and the push name from `whatsmeow_device` for the screens. `source.Source` can implement `io.Closer`; `Engine.SetConfig` and `Engine.Close` close the sources, and a closed `whatsapp.Source` returns `ErrClosed` and does not connect again. `Source.Reply` sends plain text (`channel`) or a quote (`thread`, from `wa_messages.raw`) with the message ID `MessageID(account, chat, pending ID, reply ID)`, and copies `ContextInfo.Expiration` of the target (disappearing messages); `Find` returns false. `Source.Download` writes the file of a stored row (`MediaOf`, at most `MaxDownload`). `wa_messages.media` marks a row with a file; `DB.Prune` keeps these rows until `retention`, the others until `lookback` plus one hour. `source.OneShot` builds a source for one send or download (lock wait 10 s, no wait for offline messages). `rowFromEvent` keeps the quote of a message in `wa_messages.quote_id`, `quote_author` (contact name, else `+<phone>`) and `quote_me`; `collect` adds the quoted text from `raw` and, when the author is not known, the sender name of the quoted row (`replyRef`). A WhatsApp message keeps an empty `ThreadID`, so the default reply place does not change.
- `internal/source/mattermost`: a small typed REST client, not the official module. Polling uses `GET /channels/{id}/posts?page&per_page` (newest first, stop at the cursor). Do not use `posts?since=`: it filters on `update_at` and has an unordered `LIMIT 1000`. Never call an endpoint that marks a channel as read. Sending uses `POST /posts` only.
- Mattermost thread replies: `Message.ReplyTo` has the root. `newPosts` keeps the roots of each page in `Source.roots` (at most 1,000); `GET /channels/{id}/posts` holds the roots of the replies of the page in `posts` also when they are not in `order` (checked on the Docker server, `posts_threads_2_p0.json`). Else `Source.root` reads `GET /posts/{id}`; HTTP 403 and 404 give the root ID only. A reply in a thread whose root the user wrote is `ForMe`.
- Mattermost facts that the send depends on (checked on the Docker server): `root_id` must be the thread root (a reply ID gives HTTP 400); a top-level post of the user marks the channel read and a thread reply does not, also with `set_online=false`; the same `pending_post_id` returns the first post for about 30 seconds only.
- `internal/reply`: the one send flow of the Feed and `i2a reply`. An error with `Answered() == true` means that the platform created no post (`failed`). Any other error keeps the reply `sending`; the next send of the same message, place and text calls `Replier.Find` before it posts again.
- `internal/download`: puts a downloaded file in the folder of the user. The file name comes from the sender, so `Name` keeps a base name without hidden characters, separators and leading dots; `Move` never overwrites; `Quarantine` sets `com.apple.quarantine`. The daemon writes to `<data>/tmp/` only, and the CLI moves the file with the access of its caller.
- `internal/render`: the prompt-injection boundary. Each message is one `json.Marshal` line inside a fence labelled `i2a-data-<nonce>`. Hidden characters are removed before encoding. Keep every data line starting with `{`. A message with `Message.ReplyTo` gets `reply_to {id, author, me, text}` (`Reply`, text at most 200 characters). `ReplyNote` explains it in the digest, the default inline batch and the ask prompt, not in the primer, so the primer hash does not change.
- `internal/card`: the input of `i2a card add` and the notification rule (`Plan`). Card text comes from an agent that read untrusted messages, so it gets the same sanitizing as message text.
- `internal/ask`: the one send flow of the Feed, `i2a ask` and the daemon. The text of the user is the only instruction in the ask prompt; `render.Ask` puts the card and its messages in the data fence. The ask prompt is not a template and does not change the primer hash, so an ask never restarts a reuse session.
- `internal/agent`: the drivers. The session of a space (`inbox.Session`) is the terminal handle (the address of each `orca` command) and the Claude session ID (the identity: one terminal can run Claude session A, then a shell, then session B). `ClaudeFinder` (`claude.go`) reads `<claude dir>/sessions/<pid>.json` and the environment of each pid (`kern.procargs2`, `ORCA_TERMINAL_HANDLE`). Before each send, `Orca.check` requires exactly one interactive Claude process with the stored session in the terminal (and `sendIdle` checks it again after the `tui-idle` wait, because a shell is idle too), adopts the session of a row with none, or follows the session to the one other terminal that runs it; when the files cannot be read (`ErrClaudeUnknown`) or the CLI is not Claude, Orca must report `agentIdentity`. A send with `observation: "unsupported"` is an error and deletes the session. A new terminal gets the tab name `<agent> · <space>` (`TabTitle`). A linked session has the primer hash `pending` (`inbox.PrimerPending`) and gets the primer with the next batch. `Inspector` (`inspect.go`) gives the dashboard the state of a session, the resolve step of a link and `orca terminal switch`. In `reuse` mode the store keeps the primer hash with the handle; a different hash starts a new session. Each space has its own reuse session (`sessions.space`), also when two spaces use one agent. The daemon and an ask hold `agent.Lock` of the space while they type into a terminal; a batch that waits longer than 3 minutes is `held`. Delivery is at least once: messages become `sent` only after the driver returns `sent`; `held` and errors keep them `pending`. A `dry-run` batch makes its messages `previewed`; a real driver still sends `previewed` messages.
- `internal/daemon`: `Engine` (poll, dispatch for given spaces, expire, asks, prune, `RunNow`) and `Run` (loop, one next send time for each space, asks each minute, configuration reload, `flock` lock). `api.go` is the HTTP API on the Unix socket `<data>/i2a.sock` (0600; `$TMPDIR/i2a-<hash>.sock` and `i2a.sock.path` for a long path): `GET /v1/status`, `POST /v1/run`, `GET /v1/events` (SSE), `POST /v1/reply`, `POST /v1/download`, described in `docs/daemon-api.yaml`. `/v1/reply` and `/v1/download` do not go through the loop (`actions.go`: `Engine.Reply`, `Engine.Download`; `Engine.mu` guards `cfg` and `sources`); `remote.go` has the client side (`BuildReplier`, `Download`). The loop takes each run from a channel, so the engine stays in one goroutine; the engine publishes events to a hub that drops events for a slow reader. The API never carries message, card or reply text or file content. `client.go` is the client: `i2a run --once`, `i2a status` and the dashboard (`tui.Deps.RunNow`, `tui.Deps.Events`, key `ctrl+r`) use the daemon when it answers, else they run the engine in their own process under `daemon.lock`. A space with no agent never sends.
- `internal/store`: schema version 6 renamed the `profile` columns to `space` and added `dispatches.agent` (backup `inbox.db.v5.bak`). Schema version 7 added `messages.for_me`, the table `deliveries(message_id, space, state, dispatch_id)` and `cards.space` (backup `inbox.db.v6.bak`). Schema version 8 added `sessions.agent_session` and `cards.agent_session` (backup `inbox.db.v7.bak`). Schema version 9 added `messages.reply_ext`, `reply_author`, `reply_me` and `reply_text` (backup `inbox.db.v8.bak`); `messageCols` finds the row ID of the earlier message with a subquery on `(source_id, external_id)`, so a pruned message gives 0. `Pending` fills `Message.Delivered`; `Engine.Dispatch` gives each message to each link that wants it and has no `sent` delivery; for each batch it computes the state of each message for all its spaces (`aggregate`), and `Store.FinishDispatchStates` writes the delivery and that state in one transaction; `settle` (`Store.SetStates`) handles a removed link. `SaveCards` sets `cards.space` from the session of the handle; `ask.TargetOf` and `cardSpace` use it first. `PendingCounts` gives the waiting messages of each conversation. `Requeue` makes the sent messages of a conversation after a time `pending` again, in one transaction with a `skipped` delivery (`inbox.DeliverySkipped`) for each space in `skip`; the fan-out and `aggregate` treat `skipped` like `sent`, so only the new spaces get the messages. `ExpirePending` keeps an old message `sent` when a space got it. `Engine.Dispatch` calls `refresh` (the reload of `daemon.Run`) after it reads `Pending`, so a requeue never meets older links.
- `internal/tui`: the dashboard. `i2a` opens it on the Feed tab (`tab_feed.go`), `i2a config` on Spaces. The header has three areas, `Feed`, `Spaces` and `Setup` (`areaOf`), opened by a click (`tab` also works), with `ctrl+r run now` and the next send at the right; row 1 shows the Setup sections (Accounts, Agents, Schedules, Settings, Send log: `tabNames`) or the last run (`model.lastRun`). `tab` goes through all tab IDs. The Spaces area (`tab_spaces.go`) is a list at the left (`railItems`: the spaces, Everything else = Unsorted, New conversations, Ignored, + New space) and one panel of rows (`panelRows`: setting rows that open dialogs, then conversation rows); each change saves at once through `editLinks` or `commitSpaces`, and `u` undoes the last save of the Spaces area (`ui.commitUndoable`, `ui.undo`; it compares the file as TOML under the lock, and any other save ends the undo). `config.SetSpaces` is the one way that the dashboard sets the links of a conversation. `dialog_spaces.go` has the spaces dialog of a conversation (check marks, levels, Ignore, + New space, the requeue option that calls `Store.Requeue`) and the search of all conversations (`/`, and `a` for a space). New conversations: listed, no entry, and not in `<data>/conversations-seen.json` (`seen.go`; the first listing of an account seeds it). The Feed opens only the stored URL of a source message, never a link from card text; it shows the urgency as bars (`urgBar`: `▰▰▰` high, `▰▰▱` normal, `▰▱▱` low) and the space of each card (`cardSpace`). The Feed has three panels, Spaces (`feedRail`, 100 columns or wider), Cards and Card (`model.feedFocus`): `←`/`→` move the keyboard between them, the focused panel has the accent border (`detailPanel`), `↑`/`↓` act in it, the Card panel scrolls (`cardText`, `model.cardOff`, reset for another card), and `wheel` sends the mouse wheel to the panel under the pointer; card rows start at the left edge (`cardRow`). `F` opens the space list as a pick dialog; the Feed and the Send log share one filter by space ID (`model.spaceFilter`, `activeSpace`). The footer shows only the hints that fit (`fitHints`). The card body is Markdown (`markdown.go`, glamour); `stripOSC` removes the OSC 8 hyperlinks that glamour writes for links and images, so keep it on each render. `model.go` has the layout (header with the areas, the line of the Setup sections or the last run, content, footer), the focus (list or form), the global keys (`tab`, `ctrl+r`, `/`, `?`), the mouse zones and the dialog stack. Each tab is one file (`tab_*.go`). `convRows` joins the conversations that each account lists (`loadConversations`: Mattermost `ListChannels` over the network, WhatsApp `ReadChats` from its file) with the entries of the configuration; the rows sort by the last message, newest first. Add and edit are forms in the detail panel, made with the small form engine in `form.go` (text inputs, segmented choices and switches, text areas, buttons, errors under the fields). `buildForm` makes the form of the selected item again when the selection changes or after a save. A form saves through `ui.commit(change, ...)`: `change` edits the configuration that `config.Update` reads from the file now, under `config.toml.lock`, so a change of another process to a different item stays. A form keeps its item (`form.kind`, `form.id`, `form.base`); `commitForm` opens the conflict dialog when another process changed that item. Each refresh (2 seconds) checks the hash of `config.toml` (`readConfigFile`, `applyFile`) and loads a changed file; a dirty form stays. Dialogs (`dialog.go`) are confirmations, the pick dialog (an agent, a schedule, a replacement), the input dialog (a name), the digest viewer and the key help. In Setup → Agents, `s` opens the sessions dialog of an `orca` agent (`dialog_sessions.go`): the handle, the Claude session, its name and state for each space; `l` links a handle or a Claude session ID (`Inspector.Resolve`, a confirmation for another workspace or the session of another space), `u` unlinks, `o` runs `orca terminal switch`. The detail panel shows the stored sessions only, so the 2 second refresh runs no `orca` command.
- `internal/notify`: macOS notifications. A `Note` (title, subtitle, body, click target, group) goes through a `Chain` (`NewChain`, `[notify] via`): `Orca` (the plugin in `extensions/orca`, called with `plugins.invokeCommand` on the socket of `orca-runtime.json`), `TerminalNotifier` (`-contentImage <data>/icon.png`, `-open`, `-activate`, `-group`), `Osascript` (text as script arguments, never script code). `Click` maps a stored message URL to `mattermost://` or `whatsapp://send?phone=`, and `AllowedOpen` accepts only `https`, `mattermost` and `whatsapp`. The Feed in iTerm2 holds `<data>/feed-notify.lock` and writes OSC 9 (`tui.feedNotes`, `card.Diff`, `tea.Raw`); `i2a card add` shows no card note while a Feed holds it (`FeedShows`). `i2a card add` and the Feed use `card.Plan`; the daemon notifies only for failed dispatches (`Deps.Desktop` reads `via` at each note). `render.PlainText` gives the card title with no Markdown. `I2A_NOTIFY=off` turns all notes off (the e2e harness sets it). The icon is `internal/notify/assets/icon.svg`; `scripts/icon.sh` renders `icon.png`.
- `extensions/`: the plugins of external apps, one folder for each app, embedded in the binary. `i2a notify setup` writes them to `<data>/extensions/`.
- `internal/service`: the macOS LaunchAgent `io.github.sondt2709.i2a`.

Facts about the `orca` CLI (1.4.240) that the driver depends on:

- `orca terminal show` returns `ok: true` for a closed terminal. A terminal is live when `connected` and `writable` are true and `exitCause` is null.
- After `/exit`, the terminal stays open with the shell: `connected`, `writable` and `exitCause: null` do not change. `agentIdentity` becomes null some seconds later. `terminal wait --for tui-idle` is satisfied on the shell, and `terminal send` types into it and returns `observation: "unsupported"`.
- `orca terminal rename --title` sets the custom title of the tab; the title that Claude writes does not replace it. `orca terminal switch --terminal <handle>` shows the tab.
- The pane menu (right-click in the terminal text, or ctrl+right-click with right-click paste) has "Copy Terminal ID": it copies `term_<uuid>`. The tab menu has "Copy Tab ID", which is another ID. A `term_…` text in a terminal is a link: cmd+click shows that terminal.
- The Orca CLI does not return the Claude session ID of a terminal, and `orca agent launch` cannot resume a session.
- `orphaned` is true for a running agent terminal that has no visible pane. Do not use it as a liveness signal.
- `--worktree path:<dir>` fails with `selector_not_found` when Orca does not know the folder. `orca repo add` accepts git repositories only.
- `orca terminal wait --for tui-idle` returns the error code `timeout` when the agent is busy.
- Do not pass `--prompt` to `orca agent launch` or `orca worktree create`. Orca types it while the agent starts, and it can stay in the input box with no Enter (`prompt.outcome` is still `handed-to-terminal`), or not arrive (`not-delivered`). The driver launches with no prompt, waits for `tui-idle`, then runs `orca terminal send --enter --wait-submit 30`. The stage `turn_started` proves the submission.
- `orca terminal send --enter` with no `--text` sends a bare Enter.
- Prompts are command arguments (the RPC limit is 1 MiB). Keep `inline_max_bytes` at 65,536 or less. An ask prompt drops message lines above 65,536 bytes.
- Orca sets `ORCA_TERMINAL_HANDLE` (`term_<uuid>`) in an agent terminal. `orca terminal show --terminal "$ORCA_TERMINAL_HANDLE"` returns that terminal. The e2e harness clears it, so a scenario card does not record the terminal of the test run.

The fixtures in `internal/agent/testdata` are real Orca outputs with local paths replaced.

Facts about Claude Code (2.1.318) that the driver depends on:

- Each interactive process writes `<claude dir>/sessions/<pid>.json` (`CLAUDE_CONFIG_DIR`, else `~/.claude`) with `pid`, `sessionId`, `cwd`, `name` and `procStart` (`time.ANSIC`, UTC), and deletes it at exit. The file is not documented.
- `/exit` while a shell command of the agent runs opens a dialog (exit and stop tasks, move to background and exit, stay). "Move to background" starts a process with `"kind": "bg"` that keeps `ORCA_TERMINAL_HANDLE`; only `kind` `interactive` counts as the agent of a terminal.
- `/clear` keeps the pid and writes a new `sessionId`. A command that the agent runs then sees the new `CLAUDE_CODE_SESSION_ID`.
- The process inherits `ORCA_TERMINAL_HANDLE`. `kern.procargs2` returns its environment for a process of the same user.
- The fixtures in `internal/agent/testdata/claude/sessions` are real files with the IDs, names and paths replaced.

Facts about the notifiers (checked on macOS 26.6.2):

- A bare binary cannot post with the UserNotifications API (`UNErrorDomain error 1`): it needs an app bundle. i2a ships no bundle.
- iTerm2 3.7.6 shows OSC 9 (`ESC ] 9 ; text BEL`) as a notification with the title "Alert" and the body "Session <name> #1: <text>". It ignores OSC 777. WezTerm 20240203 showed nothing for OSC 9 or 777. Only a process that owns the terminal can write OSC 9: the daemon and the agent shell have no `/dev/tty`.
- terminal-notifier 3.1.0 uses its own bundle; its icon cannot change (`-appIcon` and `-sender` are removed). A value that starts with `[` or `-` needs a `\` in front. `-open` works on a click.
- `open mattermost://<host>/<team>/pl/<post>` opens the post in Mattermost Desktop; `open whatsapp://send?phone=<n>` opens the chat in WhatsApp Desktop. A WhatsApp group has no link.
- Orca 1.4.240: no OSC 9/99/777 and no `orca notify`; a bell gives fixed text. `notifications.show` of a plugin shows `<plugin id>: <title>` and also goes to the paired phones. The plugin system is experimental and off by default (`pluginSystemEnabled`).

Facts about WhatsApp and whatsmeow that the source depends on:

- whatsmeow sends no read receipt and no presence unless the code calls `MarkRead` or `SendPresence`. Never call them. It sends delivery receipts (grey ticks).
- One set of device keys can have one connection. A second connection replaces the first (`events.StreamReplaced`). Never copy a `whatsapp-<id>.db` to a test.
- whatsmeow closes the WebSocket when the context of `ConnectContext` ends. `Conn.Connect` uses `context.WithoutCancel`, so a connect from an API request keeps the connection.
- `SendMessage` with the same `SendRequestExtra.ID` two times shows one message in the chat (checked on a real account). A send and a download (`refreshMediaConn`) need the connection.
- The QR channel ends after about 160 seconds (`QRChannelTimeout`). `PairPhone` must come after the first QR event and needs a display name `Browser (OS)` from the list of WhatsApp ("Chrome (Mac OS)").
- whatsmeow deletes the device row at `events.LoggedOut`. Event handlers run one at a time, so a network call (group name) in a handler runs in a goroutine.
- Many senders have a `@lid` address. The phone number comes from `SenderAlt`, `RecipientAlt` or the LID store.
- A disconnect always logs "Error sending close to websocket"; the source drops this warning.
- whatsmeow builds with `CGO_ENABLED=0` and `modernc.org/sqlite` (`sqlstore.NewWithDB(db, "sqlite", log)`).
- The fixtures in `internal/source/whatsapp/testdata/messages.jsonl` are real stored messages. The capture tool replaces addresses, IDs, names and texts and removes all bytes. Read its output before a commit.

## Rules

- **Writing:** use ASD-STE100 style for all text (docs, comments, errors, OpenSpec artifacts, PRs). Use short sentences, the active voice and one term for one concept. Name the specific file, command or value.
- **No personal data in committed files:** no local paths, real server names, real usernames or other project names. `task leakcheck` checks the terms in `.leakcheck.local` (not committed). `tmp/` holds local secrets and is git-ignored.
- **Fixtures must copy real responses.** Mattermost fixtures come from `capture.sh` against the Docker server. Orca fixtures come from a real `orca` run with the paths replaced. WhatsApp fixtures come from `testdata/capture` on a paired account. Do not write the shape of external data by hand.
- **A new test must be able to fail.** Break the code one time and confirm that the test fails, then restore the code.
- **E2E tests drive the real binary.** They use `test/e2e/harness` (a detached tmux session on a private socket). Wait for the screen text before you send keys. Use `Term.Press`, which sends a key again when it changed nothing. Huh can drop the first key while a form starts. Wait for text that shows only on the target screen: the dashboard draws dialogs over the tab, so the tab text stays visible under a dialog. The footer keys of a tab (for example `enter edit`) show only when no dialog is open.
- In some agent sessions, the `tmux` in `PATH` is an Orca shim. The harness skips paths that contain `/.orca/`. Set `I2A_E2E_TMUX` to choose a binary.
- **OpenSpec:** significant changes go through `openspec/changes/<name>/` (proposal, design, specs, tasks) before code.
- **PR titles** use Conventional Commits (`.github/workflows/pr-title.yml`). Merges are squash-only. The title becomes the commit subject on `main`.
- **Releases** are automatic. After all CI jobs pass on a push to `main`, the `release` job in `ci.yml` runs semantic-release (`.releaserc.json`). Each push makes a new version: `!` or a `BREAKING CHANGE` footer is major, `feat` is minor, all other types are patch. `scripts/dist.sh` builds the archives. The npm packages have exact versions in `ci.yml`; change them together. Keep `conventional-changelog-conventionalcommits` on 9.x while `@semantic-release/release-notes-generator` uses `conventional-changelog-writer` 8. Before you change a version, do a full `semantic-release --dry-run` against a local Git repository and check that `generateNotes` passes.
